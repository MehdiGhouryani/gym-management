## ۲) قواعد اجرا — برای هر ۲۵ فاز بدون استثنا

۱. تحلیل عمیق کد فعلی → ۲. طراحی معماری/داده/API → ۳. پیاده‌سازی (وب+اپ+سرور هم‌زمان در محدوده فاز) → ۴. تست چندلایه → ۵. بازبینی کد → ۶. راستی‌آزمایی نهایی (`build` + `typecheck` + `lint` + `test` سبز) → ۷. مستندسازی + کامیت/PR مستقل.

- **معیار پایان = معیار پذیرش فاز، نه نوشته‌شدن کد.** رابط بدون API، API بدون UI و UI بدون حالت‌های بارگذاری/خالی/خطا ناقص است.
- **کد مرده = بدهی:** هر فایل/متغیر/وابستگی بی‌مصرف در همان فاز حذف می‌شود؛ فایل جدید فقط با مصرف‌کننده واقعی ساخته می‌شود.
- **ممنوعیت:** حذف یا نادیده‌گرفتن تست برای سبز شدن؛ هاردکد secret؛ منطق دوباره‌نویسی‌شده که در `packages/shared` هست.
- طراحی UI هر فاز پیش از کد همان فاز انجام می‌شود (وایرفریم سبک، نه سند سنگین).

## ۳) اولویت‌بندی و تصمیم‌های باز

- **مسیر بحرانی:** فاز ۱–۵ → ۶–۱۰ → ۱۱–۱۳. تا داشبورد وب (فاز ۷) محصول قابل ارائه نیست؛ موتور مالی و امنیت (فاز ۳، ۱۱، ۱۲) قبل از هر گسترش باید قابل اعتماد شود.
- **موج ۵ بر اساس مدل باشگاه‌های هدف جلو/عقب می‌شود:** باشگاه بدون کلاس گروهی، فاز ۱۷ انتشار بتا را متوقف نمی‌کند.
- **تصمیم‌های باز (در فاز مربوطه با ADR):** 2FA مدیر · نقش مربی در اپ · چندشعبه‌ای (فاز ۲۲) · انبار و فروش جانبی و هزینه‌ها (پس از ۲۵، فقط اگر بازار خواست).
- **مرجع طراحی:** الگوهای Glofox / Mindbody / PushPress به‌عنوان چک‌لیست تجربه کاربری داخل هر فاز UI استفاده می‌شوند، نه فاز جداگانه.
