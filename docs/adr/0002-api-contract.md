# ADR ۰۰۰۲ — قرارداد API

وضعیت: پذیرفته‌شده | تاریخ: ۱۴۰۵/۰۹/۲۹

## پاکت خطا

همه‌ی پاسخ‌های خطا (از جمله ۵۰۰) از `HttpExceptionFilter` عبور می‌کنند:

```json
{ "statusCode": 409, "message": "…", "code": "MEMBER_EXISTS", "existingMemberId": "…" }
```

- `code` ثابت و قابل تشخیص برای منطق کلاینت؛ `message` فارسی برای نمایش.
- خطای غیرمنتظره: ۵۰۰ با `code: INTERNAL`؛ استک کامل فقط در لاگ سرور.

## صفحه‌بندی و لیست‌ها

- لیست‌های بزرگ (`/members`): `{ items, total, page, limit, pages }`؛ پیش‌فرض ۳۰، سقف ۱۰۰.
- لیست‌های کوچک و ثابت (پلن‌ها، نشست‌ها، تاریخچه‌ی عضو): آرایه یا `items` بدون صفحه‌بندی — کاربر یک باشگاه به‌سختی از ده‌ها پلن فراتر می‌رود؛ صفحه‌بندی اینجا پیچیدگی بیهوده است.
- جستجوی عضو: فقط رقم = شماره موبایل، وگرنه نام (منطق مشترک در `packages/shared`).

## Idempotency

- عملیات مالی (`POST /members/{id}/subscriptions` و `POST /members/{id}/payments`) هدر اختیاری `Idempotency-Key` می‌پذیرند.
- همان کلید + همان بدنه = پاسخ اصلی با همان کد وضعیت، بدون اجرای دوباره؛ همان کلید + بدنه‌ی متفاوت = ۴۰۹ `IDEMPOTENCY_CONFLICT`.
- ثبت پاسخ در همان تراکنشِ عملیات است؛ خطای نیمه‌کاره جا نمی‌ماند. مهلت نگه‌داری ۲۴ ساعت.
- جدول `idempotency_keys` مشمول RLS باشگاه است.
- دلیل: شبکه‌ی ضعیف اپ پذیرش و دکمه‌های دوبار لمس‌شده نباید دو پرداخت بسازند.

## نسخه‌بندی

- همه‌ی مسیرها زیر `api/v1`؛ تغییر ناسازگار = نسخه‌ی جدید، نه شکستن `v1`.
- سند OpenAPI از روی همان طرح‌های Zod ساخته می‌شود؛ تست همگامی جلوی ناهماهنگی سند و کنترلر را می‌گیرد.
