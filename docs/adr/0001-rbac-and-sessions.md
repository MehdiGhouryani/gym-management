قواعد اجرایی:

- `gymId` همیشه از توکن (`@CurrentAuth()`) می‌آید و هرگز از ورودی کاربر.
- نقش `ADMIN` = ادمین پلتفرم؛ `gymId` ندارد و هیچ مسیر باشگاهی ندارد. `RolesGuard` فقط OWNER/STAFF را عبور می‌دهد و `AuthService` نقش ADMIN را برای ورود رد می‌کند.
- عضو (`typ: member`) روی هیچ مسیر مدیریتی عبور نمی‌کند؛ داده‌ی خودش فقط از مسیرهای مخصوص عضو (فاز ۱۹).
- اعمال سمت سرور منبع حقیقت است؛ UI فقط همان را نمایش می‌دهد.

## نشست‌ها

- اپ موبایل: refresh token در Keychain/Keystore، access در حافظه، چرخش یک‌بارمصرف، استفاده‌ی دوباره = ابطال کل خانواده.
- وب (از این فاز): refresh token در کوکی `fulad_rt` با `HttpOnly + SameSite=Strict + Secure` (production) و مسیر `/api/v1/auth`. access token فقط در حافظه‌ی JS. تشخیص وب با هدر `Origin`.
- مدیریت نشست‌ها: `GET /auth/sessions`، `DELETE /auth/sessions/{id}`، `DELETE /auth/sessions` (ابطال همه). هش توکن هرگز در پاسخ نمی‌آید.
- رویدادهای `auth.login`، `auth.member_login`، `auth.logout`، `session.revoke`، `session.revoke_all` در لاگ ممیزی ثبت می‌شوند.

## سیاست مبدأ (CSRF)

- درخواست‌های تغییردهنده با هدر `Origin` خارج از `WEB_ORIGIN` رد می‌شوند (۴۰۳ `ORIGIN_FORBIDDEN`). کلاینت‌های غیرمرورگری Origin نمی‌فرستند و عبور می‌کنند.
- CORS با `credentials: true` فقط برای مبداهای `WEB_ORIGIN`.
- در production همه‌چیز پشت یک دامنه است؛ این سیاست همان‌جا هم برقرار می‌ماند.
