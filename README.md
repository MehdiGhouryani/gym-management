# فولاد: سامانه‌ی مدیریت اشتراک باشگاه

مونوریپوی MVP با TypeScript. بدون Docker: توسعه‌ی محلی روی PostgreSQL نصب‌شده و استقرار با PM2 و Nginx.

## ساختار

- `apps/api`: بک‌اند NestJS و Prisma (پورت ۴۰۰۰، مسیر `/api/v1`)
- `apps/web`: Next.js برای وب اعضا و `/admin` (پورت ۳۰۰۰)
- `apps/mobile`: اپ مدیر باشگاه (Expo)
- `packages/shared`: منطق وضعیت اشتراک، شماره‌ی موبایل و طرح‌های Zod
- `packages/ui-tokens`: رنگ، فاصله و فونت (همان نمونه‌ی HTML تأییدشده)

## پیش‌نیازها

Node.js (نسخه‌ی LTS، حداقل ۲۰٫۱۲)، pnpm (`corepack enable`)، PostgreSQL ۱۶ یا بالاتر، Git.
Redis تا فاز ۳ لازم نیست.

## اجرا برای اولین بار

```bash
pnpm install
cp apps/api/.env.example apps/api/.env          # DATABASE_URL را با پایگاه داده‌ی خودتان هماهنگ کنید
cp apps/web/.env.example apps/web/.env.local
createdb fulad                                   # یا از pgAdmin
pnpm db:generate
pnpm db:migrate --name init                      # اولین مهاجرت را می‌سازد؛ حتماً در گیت ثبت شود
pnpm --filter @fulad/shared test                 # تست منطق وضعیت و شماره‌ی موبایل
pnpm dev                                         # api و web
```

فایل `pnpm-lock.yaml` که بعد از اولین نصب ساخته می‌شود را حتماً کامیت کنید، چون CI با `--frozen-lockfile` اجرا می‌شود.

اپ موبایل: بخش «فاز ۲» پایین‌تر را ببینید.

## فونت وزیرمتن

- **وب:** فایل‌های `Vazirmatn-Regular.woff2` و `Vazirmatn-Bold.woff2` را در `apps/web/public/fonts` بگذارید (میزبانی داخلی). تا آن زمان Tahoma نمایش داده می‌شود.
- **اپ:** از بسته‌ی npm با نام `vazirmatn` (devDependency اپ) خوانده می‌شود. اگر مسیر فایل‌ها در نسخه‌ی نصب‌شده فرق داشت، در `apps/mobile/src/ui/fonts.ts` اصلاحش کنید؛ تا آن زمان فونت سیستم نمایش داده می‌شود و اپ خراب نمی‌شود.

## استقرار (staging و production)

روی سرور: Node، pnpm، PM2، PostgreSQL و Nginx نصب باشد.

1. `deploy/nginx.conf.example` را به‌عنوان تنظیم Nginx و TLS قرار دهید.
2. فایل‌های `.env` را روی سرور بسازید.
3. `./scripts/deploy.sh` را اجرا کنید (دریافت کد، نصب، ساخت، مهاجرت و راه‌اندازی مجدد با PM2).

## تصمیم‌های فنی ثبت‌شده

- **تاریخ:** در پایگاه داده میلادی (`DATE`) و به‌صورت `YYYY-MM-DD`؛ تبدیل به شمسی فقط هنگام نمایش. «امروز» همیشه به وقت تهران است (`todayInTehran`).
- **پایان اشتراک:** `endsOn` آخرین روز معتبر است و شامل همان روز می‌شود. پلن N روزه که امروز شروع شود، فردا N−۲ و امروز N−۱ روز مانده دارد.
- **وضعیت:** هرگز ذخیره نمی‌شود؛ از `endsOn` و تاریخ امروز با `subscriptionStatus` محاسبه می‌شود.
- **مبلغ:** عدد صحیح به تومان.
- **شماره‌ی موبایل:** همیشه به `09xxxxxxxxx` نرمال می‌شود (`normalizePhone`).
- **RLS در PostgreSQL:** در فاز ۱ با مهاجرت جدا اضافه می‌شود.

## فاز ۱: ورود و جداسازی باشگاه‌ها (در حال انجام)

### راه‌اندازی پایگاه داده با دو نقش

برنامه با نقش `fulad_app` به پایگاه داده وصل می‌شود، چون سوپریوزر و مالک جدول‌ها همیشه از RLS عبور می‌کنند. مهاجرت‌ها با نقش مالک اجرا می‌شوند (`MIGRATE_DATABASE_URL`).

```bash
# ۱) مقدارهای MIGRATE_DATABASE_URL، JWT_SECRET و OTP_PEPPER را در apps/api/.env بگذارید
pnpm db:migrate --name init                      # با نقش مالک
# ۲) ساخت نقش برنامه و فعال‌سازی RLS (با نقش مالک)
psql "$MIGRATE_DATABASE_URL" -v app_password='رمز-قوی' -f apps/api/prisma/rls/000_app_role.sql
psql "$MIGRATE_DATABASE_URL" -f apps/api/prisma/rls/001_tenant_rls.sql
# ۳) DATABASE_URL را روی fulad_app تنظیم کنید
# ۴) تست نشت داده بین دو باشگاه (روی یک پایگاه داده‌ی خالی)
createdb fulad_rls_test && psql fulad_rls_test -f apps/api/prisma/rls/rls.test.sql   # باید RLS OK چاپ شود
```

هر بار که جدول جدید وابسته به باشگاه ساختید، نام آن را به فهرست داخل `001_tenant_rls.sql` اضافه کنید و دوباره اجرایش کنید.

### استفاده از جداسازی در کد

هر کوئری روی جدول‌های وابسته به باشگاه باید داخل `TenantService.run(gymId, tx => ...)` اجرا شود. بدون آن، RLS هیچ ردیفی نشان نمی‌دهد. `gymId` همیشه از توکن می‌آید (`@CurrentAuth()`)، هرگز از ورودی کاربر.

### نقطه‌های پایانی ورود

| مسیر | کار |
|---|---|
| `POST /api/v1/auth/otp/request` | درخواست کد برای `manager` یا `member` (برای عضو، `gymSlug` هم لازم است) |
| `POST /api/v1/auth/otp/verify` | تأیید کد و دریافت access و refresh |
| `POST /api/v1/auth/refresh` | چرخش refresh و دریافت access جدید |
| `POST /api/v1/auth/logout` | باطل‌کردن نشست |
| `GET /api/v1/me` | نمایش هویت از روی توکن (نیاز به Bearer) |

- پاسخ درخواست کد همیشه یکسان است تا ثبت‌بودن یا نبودن شماره معلوم نشود. کد برای شماره‌ی ثبت‌نشده ارسال نمی‌شود.
- در حالت `SMS_PROVIDER=console` کد در لاگ سرور چاپ می‌شود. در production این حالت ممنوع است.
- access حدود ۱۵ دقیقه اعتبار دارد. refresh یک‌بارمصرف است و ۳۰ روز اعتبار دارد؛ استفاده‌ی دوباره از توکن چرخیده‌شده کل نشست را باطل می‌کند.
- ورود مدیر فقط وقتی کار می‌کند که باشگاه `ACTIVE` باشد.
- ساخت اولین باشگاه و مدیر تا فاز ۵ (پنل ادمین) با یک اسکریپت یا مستقیم در پایگاه داده انجام می‌شود.

## فاز ۱، بخش ۲: اعضا و پلن‌ها

همه‌ی مسیرها نیاز به `Authorization: Bearer ...` دارند و عضو وب (نوع `member`) به هیچ‌کدام دسترسی ندارد.

| مسیر | نقش | کار |
|---|---|---|
| `GET /api/v1/members?q=&status=&page=&limit=` | مدیر، پذیرش | فهرست با جستجو و فیلتر وضعیت (پیش‌فرض: ۳۰ مورد، حداکثر ۱۰۰) |
| `GET /api/v1/members?archived=true` | مدیر | بایگانی |
| `GET /api/v1/members/counts` | مدیر، پذیرش | شمارنده‌ی چیپ‌ها: all, active, expiring, expired, lapsed, none |
| `POST /api/v1/members` | مدیر، پذیرش | ثبت عضو (نام، موبایل، تاریخ تولد و یادداشت اختیاری) |
| `GET` و `PATCH /api/v1/members/:id` | مدیر، پذیرش | مشاهده و ویرایش |
| `POST /api/v1/members/:id/archive` و `/restore` | مدیر | بایگانی و بازگردانی (در لاگ ممیزی ثبت می‌شود) |
| `GET /api/v1/plans` | مدیر، پذیرش | پلن‌های فعال |
| `GET /api/v1/plans?includeInactive=true` | مدیر | همه‌ی پلن‌ها |
| `POST /api/v1/plans` و `PATCH /api/v1/plans/:id` | مدیر | ساخت و ویرایش پلن (حذف وجود ندارد؛ پلن غیرفعال می‌شود) |

قواعد:

- **جستجو:** اگر فقط رقم باشد (فارسی یا لاتین) در شماره‌ی موبایل جستجو می‌شود، وگرنه در نام. حروف عربی (ي ك) و ارقام قبل از ذخیره و جستجو یکسان می‌شوند.
- **فیلتر وضعیت:** `active` (بیش از ۷ روز مانده)، `expiring` (تا ۷ روز، شامل امروز)، `expired` (منقضی و در مهلت پیگیری)، `lapsed` (منقضی و خارج از مهلت)، `none` (بدون اشتراک). آستانه‌ها از تنظیمات باشگاه می‌آیند.
- **ترتیب:** نزدیک‌ترین انقضا بالا، بدون اشتراک آخر فهرست.
- **شماره‌ی تکراری:** پاسخ ۴۰۹ با `code` برابر `MEMBER_EXISTS` یا `MEMBER_ARCHIVED` و `existingMemberId` (برای دکمه‌ی «باز کردن پروفایل»).
- **بایگانی:** نشست‌های وب عضو باطل می‌شود. پذیرش بایگانی را نمی‌بیند و نمی‌تواند بایگانی یا بازگردانی کند.
- **پلن:** نام یکتا (بدون توجه به حروف) در هر باشگاه. تغییر قیمت یا مدت فقط روی اشتراک‌های بعدی اثر دارد.
- **`Member.currentEndsOn`:** آخرین روز معتبر اشتراک؛ فقط بخش اشتراک (بخش بعدی) آن را در همان تراکنشِ ثبت یا تمدید به‌روز می‌کند. فیلتر وضعیت و ترتیب فهرست روی آن ایندکس دارند.

اگر قبلاً مهاجرت `init` را اجرا کرده‌اید، برای ستون جدید یک مهاجرت بسازید: `pnpm db:migrate --name member_current_ends_on`.

## فاز ۱، بخش ۳: اشتراک و پرداخت

| مسیر | نقش | کار |
|---|---|---|
| `POST /api/v1/members/:id/subscriptions` | مدیر، پذیرش | ثبت یا تمدید اشتراک (و در صورت نیاز پرداخت همان لحظه) |
| `POST /api/v1/members/:id/payments` | مدیر، پذیرش | پرداخت بدهی؛ از قدیمی‌ترین اشتراک بدهکار کم می‌شود |
| `GET /api/v1/members/:id/subscriptions` | مدیر، پذیرش | تاریخچه‌ی اشتراک‌ها و پرداخت‌ها با جمع کل و مانده |

بدنه‌ی تمدید: `{ planId, startsOn?, price?, paidAmount, method? }`.

قواعد:

- **تاریخ شروع:** اگر `startsOn` نیاید، اشتراک معتبر از روز بعد از پایان فعلی و اشتراک منقضی از امروز شروع می‌شود. `endsOn` آخرین روز معتبر است. تاریخ دستی نباید با اشتراک فعلی هم‌پوشانی داشته باشد و حداکثر ۶۰ روز از امروز فاصله دارد.
- **مبلغ:** `price` فقط برای مدیر باشگاه است (تخفیف). اگر نیاید، قیمت پلن ثبت می‌شود و در اشتراک ذخیره می‌ماند؛ تغییر بعدی قیمت پلن روی آن اثری ندارد.
- **پرداخت:** `paidAmount` از مبلغ اشتراک بیشتر نمی‌شود. اگر بیشتر از صفر باشد، `method` (`CASH`، `CARD` یا `POS`) لازم است. پرداخت کمتر از مبلغ، بدهی می‌سازد. برای تسویه‌ی بدهی قبلی از `POST .../payments` استفاده کنید (در اپ: کلید «تسویه‌ی بدهی قبلی» بعد از تمدید این مسیر را صدا می‌زند). مبلغ بیش از کل بدهی با کد `AMOUNT_EXCEEDS_DEBT` و `totalDebt` رد می‌شود. بازپرداخت وجود ندارد.
- **هم‌زمانی:** ردیف عضو در تراکنش قفل می‌شود (`FOR UPDATE`)؛ دو تمدید یا پرداخت هم‌زمان برای یک عضو پشت هم اجرا می‌شوند.
- **بدهی:** `Member.balance` بعد از هر تغییر از روی ردیف‌های اشتراک و پرداخت دوباره محاسبه می‌شود (نه با جمع و تفریق)، پس نمی‌تواند از واقعیت دور شود. فیلتر `GET /members?debtor=true` و شمارنده‌ی `debtors` در `/members/counts` از آن استفاده می‌کنند.
- **لاگ ممیزی:** `subscription.create`، `payment.debt` و تغییر پلن و بایگانی ثبت می‌شوند.

راه‌اندازی بخش:

```bash
pnpm db:migrate --name subscriptions_balance          # ستون balance
psql "$MIGRATE_DATABASE_URL" -f apps/api/prisma/rls/002_integrity.sql   # قیدهای پایگاه داده (نیاز به btree_gist)
psql "$MIGRATE_DATABASE_URL" -f apps/api/prisma/rls/balance_check.sql   # باید هیچ ردیفی برنگرداند
```

`002_integrity.sql` این‌ها را در خود پایگاه داده اعمال می‌کند: بدهی منفی نشود، پرداخت صفر یا منفی ثبت نشود، تاریخ پایان قبل از شروع نباشد و هیچ عضوی دو اشتراک هم‌پوشان نداشته باشد. اگر `CREATE EXTENSION btree_gist` با نقش مالک مجاز نبود، یک‌بار با سوپریوزر اجرا کنید.

## فاز ۱، بخش ۴: گزارش ماهانه

`GET /api/v1/reports/monthly?year=1405&month=7` (فقط مدیر باشگاه؛ بدون پارامتر یعنی ماه جاری شمسی)

```json
{
  "period": { "year": 1405, "month": 7, "monthName": "مهر", "from": "2026-09-23", "to": "2026-10-22" },
  "revenue": { "total": 48500000, "paymentCount": 112, "byMethod": { "CASH": 0, "CARD": 0, "POS": 0 },
               "weeks": [11200000, 14600000, 9800000, 12900000], "previousTotal": 44900000, "changePercent": 8 },
  "members": { "active": 128, "newInMonth": 18 },
  "renewal": { "total": 25, "renewed": 18, "lost": 4, "pending": 3, "rate": 82 },
  "receivables": { "total": 3900000, "debtors": 9 },
  "recentPayments": [{ "id": "...", "amount": 4500000, "method": "CARD", "paidAt": "...", "memberId": "...", "memberName": "..." }]
}
```

تعریف‌ها:

- **درآمد:** جمع پرداخت‌های دریافت‌شده در ماه (بر اساس `paidAt`، نه تاریخ شروع اشتراک). مرز روزها به وقت تهران است.
- **هفته‌ها:** روز ۱ تا ۷، ۸ تا ۱۴، ۱۵ تا ۲۱ و ۲۲ تا آخر ماه. `changePercent` نسبت به ماه قبل است و اگر ماه قبل درآمد نداشت `null` می‌شود.
- **نرخ تمدید:** از اشتراک‌هایی که در این ماه تمام می‌شوند، چند درصد تا `graceDays` روز بعد از پایان (پیش‌فرض ۱۴) اشتراک جدید گرفته‌اند. آن‌هایی که مهلتشان تمام نشده و هنوز تمدید نکرده‌اند در `pending` می‌مانند و در نرخ حساب نمی‌شوند. اگر هنوز تصمیمی نیست `rate` برابر `null` است.
- **مطالبات:** جمع بدهی همه‌ی اعضا در لحظه‌ی درخواست (به ماه وابسته نیست).
- **عضو جدید:** اعضایی که در همان ماه ثبت شده‌اند. **اعضای فعال:** اعضای بایگانی‌نشده‌ای که اشتراکشان هنوز تمام نشده است.
- سال بین ۱۳۰۲ و ۱۵۰۰ و ماه بین ۱ و ۱۲ و هر دو با هم لازم‌اند.

تقویم شمسی در `packages/shared/src/jalali.ts` است (برای وب و اپ هم قابل استفاده). نوروز سال‌های ۱۳۹۵ تا ۱۴۰۷ با تاریخ‌های واقعی تست شده است. برای سال‌های دورتر ممکن است مرز سال با تقویم رسمی یک روز اختلاف داشته باشد.

## فاز ۱، بخش ۵: مستندات API و داده‌ی نمونه

### مستندات (Swagger)

با `pnpm dev` روی `http://localhost:4000/api/v1/docs` باز می‌شود (JSON خام: `/api/v1/docs-json`). در production پیش‌فرض خاموش است و با `ENABLE_DOCS=true` روشن می‌شود. CSP پیش‌فرض helmet فقط برای همین مسیر کنار گذاشته شده، چون اسکریپت‌های درونی Swagger UI را می‌بندد.

- بدنه‌ی درخواست‌ها از روی همان طرح‌های Zod ساخته می‌شود (`z.toJSONSchema`)، پس با اعتبارسنجی واقعی هرگز فرق نمی‌کند.
- پاسخ‌ها در `src/openapi/openapi.ts` تعریف شده‌اند. سه تست جلوی ناهماهنگی را می‌گیرند: هر مسیر کنترلرها باید در سند باشد و برعکس، کلیدهای `Member`، `Plan` و `Subscription` در سند باید با خروجی واقعی یکی باشد، و هر `$ref` باید مقصد داشته باشد. وقتی مسیر یا فیلد جدید اضافه می‌کنید، این تست‌ها تا به‌روزکردن سند قرمز می‌مانند.

### داده‌ی نمونه

```bash
pnpm db:seed            # باشگاه نمونه را می‌سازد؛ اگر هست کاری نمی‌کند
pnpm db:seed --reset    # داده‌ی نمونه را پاک و دوباره می‌سازد
```

با `DATABASE_URL` (نقش `fulad_app`) اجرا می‌شود، پس هم‌زمان تست می‌کند که دسترسی‌های نقش و RLS درست کار می‌کنند. در production اجرا نمی‌شود. تاریخ‌ها نسبت به امروز ساخته می‌شوند تا همیشه همه‌ی وضعیت‌ها در فهرست باشند:

| کاربر | شماره | نقش |
|---|---|---|
| رضا نیک‌خو | `09120000001` | مدیر |
| ابراهیم توکلی | `09120000002` | پذیرش |

۱۲ عضو نمونه (`09121000001` تا `09121000012`): نزدیک انقضا، منقضی در مهلت، منقضی خارج از مهلت، فعال، بدون اشتراک، دو بدهکار، یک عضو با تاریخچه‌ی دو اشتراک و یک عضو بایگانی. پلن‌ها: یک‌ماهه، سه‌ماهه، شش‌ماهه و سالانه (غیرفعال). ورود با `SMS_PROVIDER=console` انجام می‌شود و کد در لاگ سرور چاپ می‌شود.

فایل `apps/api/requests.http` یک مسیر کامل را از ورود تا تمدید و گزارش اجرا می‌کند (افزونه‌ی REST Client در VS Code یا HTTP Client در JetBrains).

### چک‌لیست تأیید فاز ۱ (روی سیستم شما)

## فاز ۲: اپ مدیر باشگاه (Expo)

### راه‌اندازی

```bash
pnpm install
cd apps/mobile
# نسخه‌ی پکیج‌های Expo را خود Expo هماهنگ می‌کند
npx expo install expo expo-router expo-secure-store expo-font expo-splash-screen expo-status-bar expo-linking \

npx expo start              # با Expo Go روی گوشی یا امولاتور
```

- API باید بالا باشد (`pnpm dev` در ریشه) و `pnpm db:seed` اجرا شده باشد. ورود نمونه: `09120000001` و کد از لاگ سرور.
- **راست‌چین:** اولین بار که اپ باز می‌شود راست‌چین فعال می‌شود ولی تا یک‌بار بستن کامل و بازکردن دوباره اثر کامل ندارد. چیدمان‌ها طوری نوشته شده‌اند که در هر دو حالت درست دیده شوند.
- **اندروید امولاتور** سیستم میزبان را با `10.0.2.2` می‌بیند و iOS سیمولاتور با `localhost`؛ نیازی به تنظیم نیست. روی گوشی واقعی گوشی و سیستم باید روی یک شبکه باشند.

### این بخش چه دارد

- ورود با کد پیامکی (شماره ← کد ۵ رقمی، ورود خودکار با کامل‌شدن رقم پنجم، ارسال دوباره بعد از شمارش معکوس).
- نشست امن: refresh token در Keychain/Keystore، access token فقط در حافظه. با ۴۰۱ یک‌بار و تک‌پرواز refresh می‌شود؛ قطع اینترنت نشست را پاک نمی‌کند.
- تب **امروز:** اعضای منقضی (در مهلت پیگیری) و نزدیک انقضا، یکجا و مرتب‌شده، با «تماس»، «پیامک» و «واتس‌اپ» (پیام آماده‌ی یادآوری). ارسال خودکار با صف سرور در فاز ۳ می‌آید.
- تب **اعضا:** جستجو (نام یا بخشی از شماره)، هفت فیلتر با شمارنده، صفحه‌بندی بی‌نهایت.
- حالت‌های بارگذاری، خالی و خطا با «تلاش دوباره».
- **پروفایل عضو:** روزهای باقی‌مانده، میله‌ی ۳۰ روزه، تماس، پیامک و واتس‌اپ، بدهی و تاریخچه‌ی اشتراک‌ها و پرداخت‌ها.
- **ثبت عضو:** نام و موبایل (ارقام فارسی و فاصله پذیرفته می‌شود)، «ذخیره» یا «ذخیره و ثبت اشتراک». شماره‌ی تکراری به‌جای خطای خشک، دکمه‌ی «باز کردن پروفایل» می‌دهد.
- **برگه‌ی تمدید (از «امروز» و پروفایل):** پلن قبلی عضو از پیش انتخاب است؛ تاریخ شروع و پایان و پرداخت کامل خودکارند. مدیر می‌تواند مبلغ را تغییر دهد (تخفیف)، پذیرش نه. پرداخت بخشی بدهی می‌سازد و «تسویه‌ی بدهی قبلی» هم‌زمان بدهی قدیمی را می‌گیرد.
- **پرداخت بدهی:** پیش‌فرض کل بدهی؛ مبلغ بیش از بدهی در همان فرم رد می‌شود.

- **تب گزارش (فقط مدیر):** درآمد ماه با تغییر نسبت به ماه قبل، درآمد هفتگی، نرخ تمدید، عضو جدید، اشتراک فعال، مطالبات و آخرین پرداخت‌ها؛ رفتن به ماه‌های قبل. برای پذیرش تب پنهان است و سرور هم ۴۰۳ می‌دهد.
- **ویرایش عضو** (فقط فیلدهای تغییرکرده فرستاده می‌شود) و **بایگانی و بازگردانی** (فقط مدیر، با تأیید). عضو بایگانی‌شده در فیلتر «بایگانی» (فقط مدیر) دیده می‌شود و اشتراک یا پرداخت جدید برایش ثبت نمی‌شود.

قاعده‌ی تاریخ تمدید (`planRenewal`) در `packages/shared` است و سرور و اپ دقیقاً یک محاسبه را استفاده می‌کنند، پس تاریخ پایانی که قبل از ثبت می‌بینید همان است که سرور ثبت می‌کند.

منطق خالص اپ (کلاینت API، قالب‌بندی اعداد و تاریخ شمسی، پیام یادآوری، ترتیب «امروز»، پیام خطا) در `apps/mobile/src/lib` است و با `pnpm --filter @fulad/mobile test` تست می‌شود.
